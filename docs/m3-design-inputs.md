# M3 設計材料（M2 レビューの申し送り）

M2 のレビューで出た「M3 への申し送り」を、流れてしまわないよう独立させたもの。
**M3 の設計を始めるときは、着手前にこれを読む。**

M3 は executor（codex / claude）の実装が中心になる想定。
そこで初めて踏む地雷が M2 の時点で見えているので、先に書き残す。

---

## 1. 最も破られやすい不変条件

`.claude/CLAUDE.md` の不変条件のうち、**M3 で構造的に破りたくなる**もの2つ。
どちらも「破ると壊れる」ではなく「破ったほうが実装が楽で、しかも動いてしまう」のが厄介な点。

### 1-1. 再実行可能性（不変条件2）

> 各ステップは**入力成果物ファイルだけから再実行できなければならない**。
> セッション再開（resume）は最適化であり、正しさの要件にしない。

**構造的な誘惑**: claude executor を書くと、`query()` の resume でセッションを繋ぎたくなる。
前ステップの文脈が残っていれば入力成果物を組み立て直さずに済み、実装が短くなり、
**しかも普通に動く**。壊れるのは「セッションが切れたとき」「別マシンで再開したとき」
「ステップを飛ばして再実行したとき」だけなので、開発中は気付かない。

現時点の**強制はゼロ**である（CLAUDE.md にもそう書いた）。clipboard executor には
resume の概念が無く、破れるコードがまだ存在しないため、テストの書きようがない。

**防衛線**: executor の実装と**同一コミット**で、以下のテストを足す。

- resume に失敗したとき fresh へフォールバックすること
- fresh 経路だけで（前ステップのセッションを持たない状態から）ステップが完走すること
- ステップ間で会話履歴に依存した値を渡していないこと
  （入力成果物ファイルを差し替えれば出力が変わることを確認する）

「あとで足す」にすると、動いている実装のあとからテストを書くことになり、
**実装に合わせたテストになって不変条件を守らなくなる**。

### 1-2. 生 session ID のログ混入（不変条件6）

> session の生 ID をログに残さない。hash または末尾識別子のみ。

1-1 と**同時に発生しうる**。session を扱い始めた瞬間、デバッグのために
Event Log へ ID を落としたくなる。これも強制ゼロ（session ID を持つ executor が無いため）。

**防衛線**: `SkillVersionInfo` に倣い、**型を先に切る**。
`versions.ts` の `skillHash` / `instructions[].hash` は
「生の値ではなく hash を持つ」ことを型で表現していて、生値を入れる場所が無い。
同じ形（例: `sessionRef: { hash: string; tail: string }`）を executor の実装より先に定義し、
生 ID を保持できる型を作らない。

## 2. Instructions 再送コストとキャッシュ戦略

### 現状

組み立ては**毎ステップ全文再送**である。8 ステップ分の総和は 60,980 bytes で、
`coding-rules.md` は implementation / fix / review の3回、
`backlog-rules.md` は review / reflection の2回送られる。

clipboard executor では**無料**（人間が貼るだけ）。
**M3 で API 実行に移した瞬間、これが実費になる。**

### 対策候補

| 案 | 内容 | 論点 |
| --- | --- | --- |
| **(a) system prompt 側へ** | `coding-rules` 等の Instructions を system prompt に置く | プロバイダのキャッシュに乗りやすい。Step ごとに宣言が違う点をどう扱うか（全部入れるか、ステップ別 system を作るか） |
| **(b) cache breakpoint を境界に置く** | prompt caching の区切りを instructions / skill / step の境界に合わせる | 組み立て順が固定なので前置部分がそのまま共通接頭辞になる。実装は最小 |

**(b) が本命**。理由は次項。

### 組み立て順の固定は、回帰防止ではなくコスト構造の防衛線

現在の結合順は **一般 → 固有** で固定されている:

```text
1. instructions/<name>.md
2. instructions/local-environment.md
3. skills/<step>/SKILL.md
4. prompts/<step>.md
```

この順序は「最も具体的な Step 宣言を最後に置く」という指示の優先順位から決めたものだが、
**キャッシュの前置と相性が良い**という副次的な性質を持つ。
共有される順に並んでいるため、先頭からの共通接頭辞が最大になり、
M2 の設計をそのまま prompt caching へ流用できる。

> **逆に、順序を変える変更は M3 のコスト構造を壊す。**
> 例えば「Step プロンプトを先頭に置いたほうが読ませやすい」といった理由で並べ替えると、
> ステップごとに接頭辞が変わり、キャッシュヒットが得られなくなる。

`test/prompt-assembly.test.ts` の Test 81（順序固定）は、
単なる回帰防止テストではなく**このコスト構造の防衛線**として扱う。
落としたり緩めたりするときは、M3 のキャッシュ戦略への影響を先に確認すること。

### 測るべきもの

M3 で API 実行に移したら、Event Log の `inputTokens` / `cacheReadTokens` が初めて埋まる。
そのとき最初に見るのは **cacheReadTokens / inputTokens の比**で、
Instructions の再送がキャッシュに吸収されているかを判定する。
（現状これらは全件 null。M1 以前から一度も埋まっていない。）

## 3. M3 前の先行作業

### `task-metadata.json` の json-schema validator

**推奨実施時期: M3 前**（`docs/m2-mechanism-migration.md` に記録済み）。

本命は **`metrics` を `integer | null` にして 0 と null を型で区別する**こと。
「読み取れないものは `null`」という Skill の指示は、`0` を許す型のままでは
推測で 0 を書いても検出できない。

M3 で executor が自動化されると、`task-metadata.json` を書くのも AI になり、
**人間が目視する機会がさらに減る**。自動化の前に形の検査を入れておく。

詳細（検査する項目、やらないこと）は機構移行レポートの第3節を参照。

## 4. codex CLI の実行方法（2026-08-18 実測）

**この節の数値と挙動は `codex-cli 0.148.0-alpha.9` を実機で叩いた結果である。**
⚠️ **M3 の実装に着手する時点で測り直すこと。** 更新が速く（下記）、
ここに書いた flag 面は数週間で変わりうる。推測で設計に書かない。

### 4-1. `--full-auto` は削除された

v0.147.0（安定版）で削除。0.148.0-alpha.9 でも復活していない（実行して確認）:

```text
error: unexpected argument '--full-auto' found
```

現在の指定方法:

| 用途 | フラグ |
| --- | --- |
| サンドボックス | `-s, --sandbox <read-only \| workspace-write \| danger-full-access>` |
| **承認の代替** | **`--approve-for-me`**（承認要求を workspace-write サンドボックスの自動レビューへ回す） |
| 外部サンドボックス下 | `--dangerously-bypass-approvals-and-sandbox` |
| プロファイル | `-p, --profile <名前>` → `$CODEX_HOME/<名前>.config.toml` をベース設定へ重ねる |
| JSONL イベント | `--json` |
| 最終メッセージのファイル出力 | `-o, --output-last-message <FILE>` |
| 構造化出力 | `--output-schema <FILE>`（最終応答の JSON Schema） |
| 作業ディレクトリ | `-C, --cd <DIR>` / `--add-dir <DIR>` |
| セッションを残さない | `--ephemeral` |
| 設定の隔離 | `--ignore-user-config` / `--strict-config` |

`resume` は**サブコマンド**（`codex exec resume [SESSION_ID] [PROMPT]`、`--last` / `--all`）。
`fork` もある。§1-1 の「resume を正しさの要件にしない」は、この resume を指す。

`--ephemeral` は不変条件2と相性が良い。セッションを残さないので
「前回の続き」に依存しようがなくなる。**v1 の既定に据える候補**。

### 4-2. pin が生命線である理由（実測）

| 事実 | 実測値 |
| --- | --- |
| 手元の実体 | `~/.codex/.sandbox-bin/codex.exe`（295 MB、署名・製品情報すべて空） |
| バージョン | `0.148.0-alpha.9`（**alpha**） |
| その実体の更新 | 作成 2026-06-19 → 更新 2026-08-18。**版番号を持たない単一パスを上書き** |
| 更新頻度 | 隣の `codex-command-runner-*.exe` 21 版から算出して **平均 4.6 日に1回**（92日で 0.131 → 0.148） |
| npm の `latest` | **0.147.0**（安定版） |
| npm の `alpha` | 0.148.0-alpha.21（**手元の alpha.9 より既に先行**） |
| 管理者 | Codex デスクトップアプリ（Electron）。`~/.codex/config.toml` も同アプリが所有 |

**`.sandbox-bin` の実体を aiw から spawn してはいけない。**
パスは固定でも中身が数日で入れ替わる。プロンプトの hash を Event Log に記録しながら
実行系だけ黙って変わる状態は、`versions.lock`（同じ番号なら同じ内容）の思想と真逆である。

**v1 の方針: npm で安定版を pin し、`CODEX_HOME` を aiw 専用ディレクトリへ向けたうえで
`--ignore-user-config` を併用する。** デスクトップアプリの `config.toml`
（marketplaces / plugins / notify）を共有したままだと、アプリ側の設定変更が実行へ混入する。

⚠️ **pin 先を 0.147.0 にする場合、この節の flag 面は測り直しになる**
（上の実測は 0.148.0-alpha.9 のもの）。

## 5. codex mcp-server 常駐案 —— v1 では採らない

`codex mcp-server` により Codex を常駐 MCP サーバーとして公開し、
aiw がツールコールでオーケストレーションする案がある。

**判断: v1 は `codex exec` のプロセス毎起動を採る。**

理由は、プロセス毎起動が**不変条件2（再実行可能性）と自然に一致する**こと。
毎回まっさらなプロセスなら、入力成果物ファイルだけから再実行できる状態が既定になり、
「前回の続き」に依存する経路が構造的に存在しない。
常駐は「長生きする状態」を持ち込む。これはこのコードベースが一貫して避けてきた設計である。

対案としては残す。**並列化フェーズで再評価の余地**がある
（プロセス起動コストが支配的になったときに初めて意味を持つ）。
その時点でも、常駐にするなら不変条件2を守る別の機構が要る。

## 6. MCP 事前検証（aiw を MCP サーバー化）

**実装時期: M3 と同時。**

### 目的

aiw の validator を**読み取り専用の MCP ツール**として公開し、
エージェントが完了を宣言する前に自己検査できるようにする。
**Fix 発生率への直接の対策**であり、M2 世代で 8/8 だった Fix 発生率を動かしうる唯一の案。

### 設計制約4点

エージェントの高速リトライによるトークン浪費への対処。根拠は実測で、
review が `approved` / `approve` という無効な値で **2 分間に 4 回** halt した事故がある
（綴りを変えて再試行し続けた。原因が伝わらないと機械的に叩き直す）。

1. **呼び出し上限: ステップあたり 3 回。**
   超過時は**エラーではなく**「宣言して `aiw run` に委ねよ」という定型応答を返す。
   エラーにすると、それ自体がリトライの燃料になる
2. **差分なし検査スキップ。** 前回検査以降に成果物のハッシュが変わっていなければ
   検査せず「変更が観測されていない」と返す
3. **応答は要約形（1〜3行）。** 詳細はディスクの成果物を読ませる。
   検査結果の全文を返すと、それを読むためのトークンで浪費が起きる
4. **全呼び出しを Event Log に記録**（回数・結果）。モデル比較の指標を兼ねる

### 公開するツールの範囲

**読み取り専用に限定する。** `aiw_approve` のような変更系は公開しない。

エージェントの自己承認を**構造的に不可能**にするためであり、
`captureIfAbsent`（エンジン専用・force 引数なし）と
`recaptureBaseline`（対話 CLI からのみ）を分離したのと同じ論理である。
呼べる場所を制限するのではなく、**呼べる関数を存在させない**。
