# M3 設計材料（M2 レビューの申し送り）

M2 のレビューで出た「M3 への申し送り」を、流れてしまわないよう独立させたもの。
**M3 の設計を始めるときは、着手前にこれを読む。**

M3 は executor（codex / claude）の実装が中心になる想定。
そこで初めて踏む地雷が M2 の時点で見えているので、先に書き残す。

---

## 1. 最も破られやすい不変条件

`.claude/CLAUDE.md` の不変条件のうち、**M3 で構造的に破りたくなる**もの2つ。
どちらも「破ると壊れる」ではなく「破ったほうが実装が楽で、しかも動いてしまう」のが厄介な点。

### 1-1. 再実行可能性（不変条件2）

> 各ステップは**入力成果物ファイルだけから再実行できなければならない**。
> セッション再開（resume）は最適化であり、正しさの要件にしない。

**構造的な誘惑**: claude executor を書くと、`query()` の resume でセッションを繋ぎたくなる。
前ステップの文脈が残っていれば入力成果物を組み立て直さずに済み、実装が短くなり、
**しかも普通に動く**。壊れるのは「セッションが切れたとき」「別マシンで再開したとき」
「ステップを飛ばして再実行したとき」だけなので、開発中は気付かない。

現時点の**強制はゼロ**である（CLAUDE.md にもそう書いた）。clipboard executor には
resume の概念が無く、破れるコードがまだ存在しないため、テストの書きようがない。

**防衛線**: executor の実装と**同一コミット**で、以下のテストを足す。

- resume に失敗したとき fresh へフォールバックすること
- fresh 経路だけで（前ステップのセッションを持たない状態から）ステップが完走すること
- ステップ間で会話履歴に依存した値を渡していないこと
  （入力成果物ファイルを差し替えれば出力が変わることを確認する）

「あとで足す」にすると、動いている実装のあとからテストを書くことになり、
**実装に合わせたテストになって不変条件を守らなくなる**。

### 1-2. 生 session ID のログ混入（不変条件6）

> session の生 ID をログに残さない。hash または末尾識別子のみ。

1-1 と**同時に発生しうる**。session を扱い始めた瞬間、デバッグのために
Event Log へ ID を落としたくなる。これも強制ゼロ（session ID を持つ executor が無いため）。

**防衛線**: `SkillVersionInfo` に倣い、**型を先に切る**。
`versions.ts` の `skillHash` / `instructions[].hash` は
「生の値ではなく hash を持つ」ことを型で表現していて、生値を入れる場所が無い。
同じ形（例: `sessionRef: { hash: string; tail: string }`）を executor の実装より先に定義し、
生 ID を保持できる型を作らない。

## 2. Instructions 再送コストとキャッシュ戦略

### 現状

組み立ては**毎ステップ全文再送**である。8 ステップ分の総和は 60,980 bytes で、
`coding-rules.md` は implementation / fix / review の3回、
`backlog-rules.md` は review / reflection の2回送られる。

clipboard executor では**無料**（人間が貼るだけ）。
**M3 で API 実行に移した瞬間、これが実費になる。**

### 対策候補

| 案 | 内容 | 論点 |
| --- | --- | --- |
| **(a) system prompt 側へ** | `coding-rules` 等の Instructions を system prompt に置く | プロバイダのキャッシュに乗りやすい。Step ごとに宣言が違う点をどう扱うか（全部入れるか、ステップ別 system を作るか） |
| **(b) cache breakpoint を境界に置く** | prompt caching の区切りを instructions / skill / step の境界に合わせる | 組み立て順が固定なので前置部分がそのまま共通接頭辞になる。実装は最小 |

**(b) が本命**。理由は次項。

### 組み立て順の固定は、回帰防止ではなくコスト構造の防衛線

現在の結合順は **一般 → 固有** で固定されている:

```text
1. instructions/<name>.md
2. instructions/local-environment.md
3. skills/<step>/SKILL.md
4. prompts/<step>.md
```

この順序は「最も具体的な Step 宣言を最後に置く」という指示の優先順位から決めたものだが、
**キャッシュの前置と相性が良い**という副次的な性質を持つ。
共有される順に並んでいるため、先頭からの共通接頭辞が最大になり、
M2 の設計をそのまま prompt caching へ流用できる。

> **逆に、順序を変える変更は M3 のコスト構造を壊す。**
> 例えば「Step プロンプトを先頭に置いたほうが読ませやすい」といった理由で並べ替えると、
> ステップごとに接頭辞が変わり、キャッシュヒットが得られなくなる。

`test/prompt-assembly.test.ts` の Test 81（順序固定）は、
単なる回帰防止テストではなく**このコスト構造の防衛線**として扱う。
落としたり緩めたりするときは、M3 のキャッシュ戦略への影響を先に確認すること。

### 測るべきもの

M3 で API 実行に移したら、Event Log の `inputTokens` / `cacheReadTokens` が初めて埋まる。
そのとき最初に見るのは **cacheReadTokens / inputTokens の比**で、
Instructions の再送がキャッシュに吸収されているかを判定する。
（現状これらは全件 null。M1 以前から一度も埋まっていない。）

## 3. M3 前の先行作業

### `task-metadata.json` の json-schema validator

**推奨実施時期: M3 前**（`docs/m2-mechanism-migration.md` に記録済み）。

本命は **`metrics` を `integer | null` にして 0 と null を型で区別する**こと。
「読み取れないものは `null`」という Skill の指示は、`0` を許す型のままでは
推測で 0 を書いても検出できない。

M3 で executor が自動化されると、`task-metadata.json` を書くのも AI になり、
**人間が目視する機会がさらに減る**。自動化の前に形の検査を入れておく。

詳細（検査する項目、やらないこと）は機構移行レポートの第3節を参照。
