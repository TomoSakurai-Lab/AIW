## 3. Fix 率激減（95% → 25%）の要因分解

### 3.1 材料（実測のみ）

| 候補要因 | 実測 |
| --- | --- |
| **母集団の違い** | **仮説は不支持**。95% 世代 21件中 aiw 系 2 / ソーク 20件中 aiw 系 1（task-metadata の taskName / summary で分類）。**両世代とも客先タスク中心** |
| モデル | 95% 世代内で 未指定1 → luna 6 → sol 4 が混在。sol の 95% 世代内 Fix 率 75%（3/4）。ソークは sol 固定 |
| 施策の時系列 | Verification Data（08-18）→ sol pin（08-20）→ ガードレール配線（08-21）が **8日間に密集**。世代セルの最大 n は 6 |
| Fix 原因分類（95% 世代・直近11本） | 実装起因 8 / research 起因 5（併記 4） |
| **Fix 原因分類（ソーク fix 5本・個別読み取り）** | **実装起因のみ 2**（tougai-hishou-selectors / drag-range）**、research 起因のみ 2**（top-screen-impl / hishou-filter-look）**、併記 1**（row-select: M1 実装 + M2 research） |

### 3.2 解釈

**結論: 施策パッケージとして効いた。個別寄与は分離不能。** Verification Data・sol 固定・
ガードレール配線が8日間に密集しており、どの組でもセル n が 6 以下のため、統計的な帰属はできない。

そのうえで方向性の示唆を2つ書く（断定はしない）:

1. **実装起因の絶対数の減りが大きい**: 20本あたり換算で 実装起因 約8 → 3、research 起因 約5 → 3。
   ガードレール（ac-manifest / measurement-completeness＝AC 脱落型の実装起因を狙った施策）の
   標的側がより大きく減っており、施策の狙いと整合する。ただし n=5 の内訳なので示唆止まり
2. **母集団交絡は消えた**: 実測により「95% は aiw 改修が多かったから」という説明は棄却された。
   残る交絡はモデルと施策時期の2つ

**早期終了バイアスの注記**: 劇的な変化を見てソークを 14日 → 7.5日 に短縮した以上、効果量は
過大評価側に歪みうる。25% は確定値ではなく **n=20・CI ±19pt の観測値**として扱うこと。
「95% から下がった」は CI を考慮しても言える。「25% に定着した」はまだ言えない。

## 5. 運用の安定性

**観測期間は 7.5 日である**（08-21 15:47 JST 〜 08-28）。当初計画は 2 週間（〜09-04）だったが、
主要観測対象（Fix 率）が n=17 時点で確定的に変化していたため短縮した。
時間依存の事象（認証切れ・フレーク率の週次変動）はこの期間では観測できていない。

| 項目 | 実測 |
| --- | --- |
| 回転数 | ソーク **2.7 本/日**（20本/7.5日）。参考: v6 期 2.0、M1/M1.5 期 1.7（各 Event Log 窓の完了数/暦日） |
| executor 故障 | **exec.failed 3件 = 全て codex タイムアウト**（08-25 ×2: 2037s/1808s、08-28 ×1: 1800s。上限 1800s）。いずれも後続実行でタスクは完走 |
| halt | ソーク窓の workflow.halted は手順起因（status.step 書き換え忘れ等）のみ。escalation 0 |

### 5.1 ⚠️ consumer-presence: 偽陽性 8 件、**うち 7 件が素通りされた（脱感作は既に実績）**

ソーク窓で consumer-presence の validation.failed は **8件**。全件が
`consumer root does not exist: Primal.Template.Web.Front/ClientApp/src`——**実在するパス**であり、
validator が root を runtime 基準で解決している（または Codex に書かせるパス基準が未定義）疑いが濃厚。
真の違反（consumer 0件）は 1 件も検出していない。

**review がこの report に言及したのは 20 タスク中 1 件のみ。残り 7 件は AI レビュアーも素通りした。**

diff-scope 設計時の警告「常に違反を出す validator は誰も見なくなる」は、懸念ではなく
**7 回分すでに起きた実績**になった。人間だけでなく review（AI）も慣れる。放置すると、
consumer-presence が本来狙った型(1)（中核未実装）の検出力を一度も計測できないまま
アラート疲れだけが定着する。**次のエンジン修正枠の筆頭**とする根拠はこの実測である。

> **2026-09-01 追記（修正後）**: 原因は「validator が root を runtime 基準で解決している」
> の側だった（Codex 側のパス基準は正しい）。KI-09 系譜 #11 として修正済み。
> 併せて全期間を数え直した——ソーク窓の 8 件は、`consumer-presence` 導入以降の
> 偽陽性 **10 件**（2026-08-20〜08-28）の一部である。
> 同期間の `passed` は **0 件**。つまりこの validator は一度も検査を完走しておらず、
> **検出力は未計測**。修正後が初計測になるので、件数を前世代と比較しないこと
> （`docs/baseline.md` の観測項目 5）。

### 5.2 CLI 破損とフォールバック（口頭報告のみ・ログ裏付けなし）

ソーク初日に「CLI が壊れ、exec 5〜7 本を clipboard フォールバックで完走、同一版の再インストールで
復旧」という口頭報告があった（このとき「1回目は修理、2回目は停止」の運用ルールを設定）。
**Event Log には痕跡がない**: 08-19 以降、implementation の exec.started で executor が
clipboard のものは 0 件、該当期間（08-21〜23）の exec.failed も 0 件。

**数えない**（盛らない原則）。これ自体が「会話で報告された運用イベントが文書化されない」という
記録の欠落の実例でもある。
